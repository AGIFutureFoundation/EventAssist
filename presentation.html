EventAssist — Presentation to win the iPhone

60-second script, then judging map. Demos 5:30–7:00pm PT, Patch the Conference.

Slide 1 — The problem (10 seconds)

Conferences are broken in three simple ways: you miss the right talk, you never meet the right person, and your plan clashes. Lists don't fix that. A graph does.

Slide 2 — The graph (10 seconds)

One shared FalkorDB graph: Speaker → Talk → Topic, Attendee → Topic, Attendee → Met → Attendee, Attendee → Plans → Talk. Concierge, networking, and schedule agents all read and write the same graph.

eventassist graph, 19 nodes, 26 edges, loaded first

Who should Ava meet? Priya Nair (Agents, GraphRAG) and Tom Rivera (GraphRAG). Not Marcus Lee — Ava already met him. Meet Priya, and the next run drops Priya. That is memory across sessions.

Slide 5 — Schedule + workshops (10 seconds)

Ava's plan clashes at 14:30. Alternative: GraphRAG at 16:00. Deep workshop overviews, with attendees per workshop, are in workshops.md — including Priya as the bridge to Robotics, the niche talk.

Slide 6 — Email + marketing agents (10 seconds)

Same graph, new agents: personalised introduction emails and workshop marketing copy, grounded in shared topics and paths. Drafts only, for approval — never sent automatically. That is how EventAssist scales from a demo to a real event tool.

Slide 7 — Judging map

  • Graph at the core: multi-hop, shared state, memory — not rows in a table
  • Explainable: every answer shows its path
  • Real problem: missed talks, missed people, clashing plans
  • Working demo: app.html, no server, no token, plus live FalkorDB queries

Primary track: FalkorDB, $1,500 or phone-or-cash. Do not dilute it with a second track on stage.

Slide 9 — Tech stack (show this slide, don't just say it)

  • Graph database — FalkorDB Cloud: instance-si114dlr3, graph eventassist, Cypher in FalkorDB Browser. Load with load_graph_complete.cypher, query with queries_complete.cypher and patterns.cypher.
  • Graph model — 19 nodes, 26 edges: 3 speakers, 4 talks, 5 topics, 4 attendees, 3 timeslots; GIVES, ABOUT, INTERESTED_IN, MET, AT, PLANS. One shared graph for all agents — no separate tables per agent.
  • Agents — Python 3.12, stdlib only: concierge.py / agents.py (Concierge, Networking, Schedule), agents_email_marketing.py (email + marketing drafts only, never sent). test_eventassist.py: 7 tests, all passing.
  • Working product — HTML/CSS/JavaScript, offline: product_v2.html embeds the same graph and agents' logic, so judges can run it with no server, no token, no install. Attendee + topic selectors, live memory update, workshops deep, judges checklist.
  • Data at scale — contacts, aggregates only in the demo: 12 ZoomInfo files, 3,678 rows → 3,476 unique contacts, 2,873 unique emails. contacts_load.py batches Contact → WORKS_AT → Company / IN_INDUSTRY → Industry / LOCATED_IN → City. No individual email, phone, or street address is in the demo or the GitHub bundle.
  • Honest limits: Docker was not available in this VM and falkordb-py was not installed, so the live demo runs offline here and is verified in FalkorDB Browser with Cypher. requirements.txt lists falkordb>=1.0 for a server deployment.
  • Deliberately NOT in the primary demo: Bright Data, TrueForge/OpenAI, and Qodo are not stacked on stage. One track, clean: FalkorDB. That is a choice, not a missing piece.

FalkorDB (Cypher) → Python agents (stdlib) → offline HTML product → same queries in Browser for live proof
